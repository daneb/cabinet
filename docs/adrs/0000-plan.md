# ADR-0000: Plan — from analysis board to repertoire study tool

**Status**: Active — Track A complete, Track B complete (2026-05-17)
**Date**: 2026-05-17

## Purpose

This index ADR records the **plan** that the rest of the 0001–0005 ADRs decompose. It exists so that future-you (or anyone reading the repo) can see the shape of the whole intent in one place rather than reconstructing it from the leaf ADRs.

## The shift

Cabinet today is a **single-line analysis board** with engine support, named-line saves, and a tasteful UI. That is what it was built as and it does that job well.

What it needs to become is a **repertoire study tool** — specifically, the tool the author uses to work through Simon Williams' *The Iron English*. That book is structured as a tree (mainline + sub-lines + transpositions + author commentary). The current linear-history data model cannot represent it without losing alternatives every time the user explores one.

These are different products. The shift is not cosmetic.

## The ADRs

| ADR | What | Why now |
|---|---|---|
| **0001 — Move tree data model** | Replace `history[]` + `cursor` with a node-keyed tree + transposition index. | Foundation. Nothing else works without this. |
| **0002 — Performance pass** | esbuild build step, memoize Board/Square, throttle engine updates, swap smooth-scroll for auto. Optional: typed-array board. | Tool is unusably sluggish today; fixing this in parallel with 0001 keeps the daily-driver experience tolerable while the bigger model lands. |
| **0003 — PGN import/export** | Parse/serialise PGN into the tree from 0001. | The content (Williams' book) exists in PGN. Without import, the tree from 0001 is an empty room. |
| **0004 — Study state and drill mode** | Per-node `status` / `lastSeenAt` / `reviewCount`; chapter tags; drill-from-memory mode. | The whole point of loading the book is to commit it to memory. The tool must close that loop. |
| **0005 — Test harness for game-core** | `node:test` runner, perft suite, SAN round-trip, tree invariants, PGN round-trip. | Every ADR above touches `chess.js`. Doing them without tests guarantees subtle corruption of stored positions — a constitution violation. |
| **0006 — Disk-backed persistence** | `GET/POST /api/saves` on the dev server, writes to `data/saves.json`. localStorage as fallback. | Study history must survive browser data clears. Disk persistence makes saves backup-able. |

## Sequencing

Two tracks, run in parallel where possible.

### Track A — make it fast (one afternoon, week 1)

ADR-0002 steps 1–4. No model changes. Just removes the sluggishness so daily use is tolerable while Track B is in flight.

- Add esbuild build step
- Memoize `Board` and `Square`
- Throttle engine updates, add depth control
- Drop `behavior: 'smooth'` from move-list scroll

### Track B — make it correct (weeks 2–4)

Order matters here. Each step depends on the previous.

1. **ADR-0005 part 1**: stand up `node:test`, write the perft suite at depth 2–3. Establishes the safety net for everything that follows.
2. **ADR-0001**: implement the move tree. Migrate v1 saves to v2 with the validation assertions. Run perft + new tree invariant tests; they must pass.
3. **ADR-0003**: implement PGN parse + serialize. Add `parseSAN` to `chess.js`. Round-trip tests against the corpus must pass. **Load the actual Iron English content.** This is the milestone where the tool starts being useful for its real purpose.
4. **ADR-0004**: study state badges in the move list, drill mode, chapter tags. The tool now does what a paper book cannot.

### Track C — only if needed (week 5+)

- ADR-0002 step 5 (Uint8Array board). Defer until profiling after tracks A+B still shows `chess.js` in the top frames. Likely unnecessary.
- ADR-0005 extensions for any new module added.

## Non-goals

- Cloud sync, multi-user, mobile. This is a single-user desktop tool on one laptop.
- Replacing Stockfish. The engine is fine; we just talk to it too often.
- A general chess GUI competing with ChessBase or lichess. The scope is opening repertoire study, and specifically *The Iron English*. Other books will inform the model later; for now they are out of scope.
- A framework migration (Next, SvelteKit, Tauri-ification). The current React + esbuild + static-file shape is right-sized. Revisit if the constraints change.

## What success looks like

By the end of Track B:

1. Opening Cabinet on a fresh tab is sub-second (Track A).
2. Loading a PGN of *The Iron English* Chapter 3 takes <2 seconds and produces a tree with the mainline, all sub-lines, and Williams' annotations intact.
3. The move list shows the chapter as indented PGN-style, with status badges showing what's known and what's unseen.
4. Drill mode lets the author play the chapter from memory; misses are flagged and reviewable.
5. Every saved line is preserved across the migration (constitution's hard rule).
6. `npm test` passes, including perft at depth 3.

That is the bar. Anything beyond is gravy.

## Risk register

| Risk | Likelihood | Mitigation |
|---|---|---|
| v1 → v2 migration loses a saved line | Low | Migration leaves v1 key in localStorage for one release; validation asserts mainline equality. |
| `parseSAN` has a subtle bug, corrupts an imported tree | Medium | Round-trip test against corpus; parser cross-checks every SAN against `legalTargetsFrom`. |
| Engine throttling makes analysis feel slow | Low | Depth and debounce are exposed as user-tunable; defaults conservative. |
| Refactor breaks `applyMove`, all stored positions silently wrong | Medium without tests, low with tests | ADR-0005 perft suite is the regression net. |
| Drill mode UI sprawls and never ships | Medium | Ship a minimal version (single side, mainline strictness) first; iterate from real use. |
| Scope creep — "while I'm here, let me add cloud sync / mobile / a server" | High (self-imposed) | This ADR's non-goals section. Re-read before each session. |

## A note on style

These ADRs follow the same conventions used in the Forgiven IDE repo: title with status and date, context-before-decision, explicit consequences (positive/negative/neutral), out-of-scope section, open questions. The intent is that each ADR can be read in isolation and is honest about what it doesn't yet answer.

Cabinet is a small project. The ADRs are not a process burden; they are the record of why decisions were made so that six-months-from-now-you doesn't have to re-derive them from the code.
